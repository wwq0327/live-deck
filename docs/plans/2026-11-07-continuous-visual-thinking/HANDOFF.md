## 3. 先做的具体动作

从 S01 开始，先建立可以在 Node 中运行的纯语义 Store，使用静态操作验证增量增加、撤回和修正；同时建立 S02 的输入账本。不要先改麦克风、加动效或换模型。

S03 把验收文字按时间顺序变成事件，先用受控响应证明“不会丢信息、不会错写”。随后 S04 用同一批事件跑真实 Flash，判断关系理解是否成立，再进入 S05 与画面联调。

任何一个阶段发现协议冲突，应先同步协议与相关 Issue。不能让模型临时发明第二种字段名，再在前端加兼容分支凑通。

## 4. 每项任务的完成流程

1. 只实现当前 Issue 范围；使用 `codex/` 前缀分支或项目既有分支约定。
2. 先读现有代码，复用配置、本机服务边界、ASR 和已经通过的修复。
3. 完成与风险相称的单元、竞态或浏览器检查，运行 `npm run check`、`npm test`。新增模块要进入检查范围。
4. 提交可审核 PR：说明行为变化、验证方法、真实执行结果和未完成项，链接当前 Issue。
5. 有 Key 才能证明真实模型行为；无 Key 只能报告确定性测试及降级路径。没有人工检查就不能写“视觉验收通过”。
6. 完成全部验收后再关闭对应 Issue。总任务在 S10 的实测与人工检查完成前保持打开。

本交接不新增应用发布、收费服务、外部消息或删除数据的授权。任务需要这些动作时按用户当次授权执行；普通本地开发和验证无需重复询问。

## 6. 评审关注点

- 是否真正建立了跨句关系，还是又退成最后一句标题？
- partial/final、显式讲话纠正和人工编辑是否正确区分？
- 新增输入能继续处理，旧来源改写能重算，两者是否混为一谈？
- 是否为了跟上而静默跳过 final 或只考虑最后一句？
- DOM 对象是否保留身份，修正是否只影响相关元素？
- 是否保留了否定、条件、问题、设想、说话人归属和概数？
- 时间与费用是否来自实测，仍未验证的部分是否明示？
